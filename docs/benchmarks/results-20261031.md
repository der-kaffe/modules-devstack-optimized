# Evaluación experimental: resultados observados y aceptación parcial

## Alcance y objetivo

Se comparan implementaciones concretas de Glance y Placement, conservando el resto de OpenStack original. La pregunta es qué cambia funcionalmente y en rendimiento al sustituir uno o ambos servicios; no se presupone una ventaja de Go. Este informe complementa el informe inicial de auditoría y su diagnóstico de capacidad, que posteriormente se resolvió para cargas HTTP acotadas.

La revisión de producción es `fa116a89b8bcd9e7c2d250c0a8b06800f0c29fa1`. El código experimental permanece como cambios locales sin staging ni commits. Los hashes de instrumentos usados durante SHOW v3 están archivados en `infrastructure-recovery-20261031b/official-instruments-v3`; las modificaciones posteriores del controlador no sustituyen esa instantánea.

## Diseño, laboratorio y variables

El host tiene Debian 13, Ryzen 5 7520U y unos 7 GiB físicos. La VM DevStack conserva su configuración persistente original de 6 GiB y cuatro vCPU. Los bloques HTTP se ejecutaron temporalmente con 4 GiB, un worker por API y Nova/Neutron detenidos exclusivamente durante dichas ventanas. Los cambios de configuración se respaldaron y restauraron. No se modificó código productivo para favorecer los resultados.

La matriz es A=Glance Python/Placement Python, B=Go/Python, C=Python/Go y D=Go/Go. El resultado integrado sería una sustitución de dos servicios, no una reescritura completa de OpenStack. Deben permanecer constantes hardware, perfil, imagen, flavor, red, autenticación, cachés y cargas; las diferencias inevitables se declaran por campaña.

Para SHOW v3 se emplearon cinco pares independientes, orden Python/Go alternado entre pares, concurrencia uno, 30 segundos de calentamiento y 90 de medición. Se conservaron todas las ventanas. Se midieron tiempo monotónico por solicitud, status/semántica, CPU por cgroup, PSS/RSS y actividad de swap. La aceptación exigió hashes de datos crudos, reloj válido, membresía de procesos estable, limpieza y restauración final. Hubo diez ventanas válidas, cero errores HTTP y cero swap-out durante cada ventana.

Se igualaron los controles observables de MySQL antes de este bloque: versión 8.0.46, buffer pool de 16 MiB, max_connections=1024, innodb_flush_log_at_trx_commit=1 y sync_binlog=1. Los servidores y esquemas permanecieron separados. El intento fallido de ajuste dinámico se conserva. Los futuros experimentos de escritura con catálogo Python aislado requerirán un protocolo nuevo y pilotos propios; no se mezclarán con este bloque.

## Coste de autenticación y atribución

La reducción de CPU del proceso Go no equivale a ahorro del sistema completo. La mediana de CPU de Keystone por solicitud correcta del API fue aproximadamente 0 ms con Python y 8,691953 ms con Go. El middleware Python utiliza su caché de tokens; el autenticador Go valida cada token de usuario contra Keystone y sólo conserva en caché su propio token de servicio. Esa diferencia está en el código existente y no se cambió para favorecer ninguna implementación.

Otros procesos conservan métricas separadas: MySQL original, MySQL experimental, Apache, Keystone y recolector. MySQL original presentó aproximadamente 1,404424/0,061260 ms CPU por operación Python/Go; MySQL experimental, 0,044962/0,995747 ms; Apache, 0,561201/0,869629 ms. Estos procesos también atienden actividad auxiliar del laboratorio. No se suman indiscriminadamente ni se atribuye su consumo íntegro a Glance. Falta una comparación oficial del coste conjunto con atribución suficientemente controlada.

El resultado observado admite simultáneamente menor memoria del API Go y peores latencia/goodput de SHOW en este despliegue. No permite atribuir el efecto exclusivamente al lenguaje: intervienen middleware, autenticación, drivers, workers, pools, esquemas y cachés.

## Controlador, fallos y restauración

El controlador nuevo prepara catálogos y stores sintéticos aislados, conserva identificadores de recuperación, limita duración/espacio/memoria y utiliza locks de host e invitado. El apagado está condicionado a bytes y metadatos de configuración, servicios originales, inventario/allocations, ausencia de unidades propias y XML persistente original. Si falla, deja NEEDS_ATTENTION y mantiene el laboratorio disponible para reparación.

El primer prototipo falló al no disponer de muestras comunes de recursos; la investigación posterior identificó una dependencia `sample_processes.py` ausente en el directorio remoto nuevo, por lo que el recolector no arrancaba. La hipótesis inicial de una ventana demasiado corta no explicaba la causa; además detectó tres servicios Nova inactivos tras restaurar los workers. Rechazó el apagado. Se reparó el orden de arranque de esos servicios, se verificaron nuevamente configuraciones/recursos y finalmente se apagó ordenadamente. No se ha demostrado todavía la causa exacta de sus fallos de arranque. El intento y la reparación permanecen separados.

La revisión posterior exige comprobar el PID systemd y la posesión real del flock B15 sobre su inode, además del marcador HELD. Un test local con un proceso real comprueba que el bloqueo retenido pasa y que, tras liberarlo, el mismo marcador obsoleto se rechaza. También se rechazan unidades ajenas y PID ausente. Esto no sustituye el ensayo completo de aborto/restauración del controlador en la VM.

En una reanudación anterior, el nuevo piloto normal de ocho segundos se bloqueó antes de arrancar: AC=0, batería 100 %. No hubo mutaciones del invitado. El control de corriente permanece vigente; se necesita alimentación para las pruebas reales pendientes y la campaña prolongada. No se lanza un job largo cuyo controlador no haya superado aún los ensayos completos normal y SIGTERM.
