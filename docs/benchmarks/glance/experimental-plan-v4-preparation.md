# Preparación v4: servicios aislados y campaña finita

La campaña v3 validó sólo show/c1 con cinco pares. Sus datos, fuentes y protocolo se conservan. La latencia y goodput favorecieron a Python en ese caso, mientras CPU y PSS del proceso API fueron menores en Go. El desglose mostró mayor CPU de Keystone con Go. El código autentica al usuario en Keystone en cada llamada; la caché sólo contiene el token del validador de servicio. No se modificará esa arquitectura para mejorar resultados.

Las escrituras prolongadas sobre el catálogo original dejarían tombstones propios. Para ampliar la matriz sin acumularlos allí se probó un Glance Python original con schema y store independientes dentro de la misma VM. Usa `/bin/uwsgi`, el mismo virtualenv, entrada WSGI, middleware y credenciales originales; `OS_GLANCE_CONFIG_DIR` selecciona únicamente archivos privados. El original no se edita. Los pilotos CRUD y descarga 16 MiB pasaron. La parada se corrigió para conservar KillMode=process y SIGTERM del original; el intento parcial anterior se retiene.

El siguiente controlador deberá abrir sesiones finitas con VM de 4 GiB y perfil de workers de hasta 7200 segundos, preservando XML persistente de 6 GiB. Cada caso tendrá backend MySQL nuevo y schemas separados Python/Go, ambos con controles verificados iguales y stores exclusivos. Así los casos no heredan filas de casos anteriores ni alteran el catálogo original. Los cinco pares de un caso comparten su despliegue; se registrará la acumulación de tombstones propia del tratamiento, sin purgar tablas originales ni ocultar intentos.

Se prevén bloques de hasta cuatro casos por sesión, con arranque y restauración completos entre sesiones. El job completo tendrá plazo absoluto finito, locks host/B15, inhibidor temporal de suspensión, reservas de memoria/disco, vigilancia de swap/OOM, batería/AC y logging persistente. El token de carga se emitirá de nuevo antes de cada caso y nunca se imprimirá. Cada caso conserva warm-up de 30 segundos, medición de 90 y cinco repeticiones pareadas alternadas. La cobertura prevista comprende los 19 casos calibrados; no se declarará completa por un subconjunto.

Antes de congelar v4 y ejecutar oficialmente, el controlador debe superar un piloto normal y un aborto por SIGTERM con restauración verificable y VM OFF. El apagado se permite únicamente después de verificar rutas, archivos, servicios, inventario y allocations. Una restauración fallida conserva evidencias y termina en NEEDS_ATTENTION con VM disponible para reparación. El controlador anterior de calibración no cumple ese gate de apagado desatendido y no se reutilizará para esta campaña larga.

Los componentes auxiliares se analizan por separado. Una caída de CPU del proceso Go no se interpretará como ahorro del sistema completo. Las campañas v3/v4 y los pilotos no se combinarán como un único experimento; la nueva configuración requiere su protocolo propio y fuentes congeladas.
