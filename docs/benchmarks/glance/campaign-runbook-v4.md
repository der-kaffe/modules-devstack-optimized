# Campaña v4 de Glance: catálogos aislados y ejecución secuencial

Estado del protocolo: DRAFT hasta validar pilotos aislados, controles locales y recuperación. No ejecutar official con estado draft. Mantener los datos SHOW v3 y sus fuentes intactos; v4 comprende exclusivamente los otros dieciocho casos. No se agrupan solicitudes, pares o percentiles entre versiones.

La implementación Python es el código/WSGI/virtualenv original con configuración privada, schema y store propios. Go tiene schema y store distintos en el mismo MySQL experimental, nuevo por caso. Se leen controles del servidor original sin cambiarlo; sólo se ajusta el experimental. Se registran hashes de fuente Python, dependencias, binarios Go y entorno efectivo saneado. El nombre `experimental-mysql` representa ambos schemas; `original-mysql` queda separado. Los pilotos iniciales conservaron el nombre heredado `go-mysql`, aunque ese proceso ya servía ambos schemas.

Cada caso oficial exige cinco pares alternados, treinta segundos de warm-up y noventa de medición. Una única implementación recibe carga cada vez. Un caso ocupa una sesión de VM completa y los pares comparten ese despliegue; tras cada ventana se limpian recursos propios. Cachés y tombstones pueden persistir dentro del caso: es una limitación declarada, no se purga SQL original para disimularla. La unidad estadística es el bloque temporal pareado; los intervalos bootstrap son descriptivos con n=5.

Antes de cada sesión, el controlador comprueba AC, reserva de host, disco, VM OFF/UUID/XML, lock host y ausencia de otro dueño del lock B15. El perfil invitado adquiere B15 antes de modificar workers. El preflight de APIs/recursos se hace dentro de esa exclusión. No ejecutar tests, compilaciones ni otros benchmarks durante las ventanas.

La fuente se copia a un bundle privado con manifiesto SHA-256. El supervisor comprueba ese manifiesto antes de cada caso. No editar el bundle durante una campaña. Mantener separados un cambio de instrumentos, una nueva versión de protocolo y la reanudación de datos existentes. Cada intento utiliza salida y namespace nuevos; las imágenes borradas pueden dejar tombstones, por lo que no se reutilizan UUID de un intento anterior.

`glance_suite.py` conduce casos secuenciales mediante `glance_lab_campaign.py`. Los JSON de entrada declaran protocolo, casos, ruta de salida nueva, bundle/manifiesto, binarios, payloads y SSH estricto. No contienen valores de tokens. La VM arranca temporalmente con4GiB y restaura inmediatamente el XML persistente6GiB; la configuración final debe coincidir byte a byte. Los procesos experimentales se vinculan al perfil finito mediante systemd.

El recolector debe importar sus dependencias en un directorio remoto nuevo y producir muestras antes de iniciar carga. Las rutas se cambian con hashes de respaldo; el guardián invitado también puede restaurarlas. El controlador tiene watchdog de memoria, disco, datos de colector, OOM y swap. Las consultas de libvirt fijan `LC_ALL=C`, también bajo systemd de usuario.

La política prospectiva de host v4 exige al menos768MiB disponibles, ningún OOM, PSI full avg10<1% y ausencia de swap-out>=1MiB/s durante9s consecutivos. Las ráfagas aisladas y la ocupación de swap se conservan en el reporte. En el invitado, la aceptación exige cero swap-out por ventana. Los umbrales constan en el protocolo antes de official y no se ajustan durante una campaña para aceptar un resultado.

La ejecución prolongada utiliza una unidad transitoria del propio usuario, RuntimeMaxSec finito, TimeoutStopSec suficiente para restaurar, MemoryMax y CPUQuota explícitos, logging persistente e inhibición de suspensión. `glance_suite.py` propaga SIGTERM a su hijo; éste detiene la carga y restaura. Para abortar se debe señalar exclusivamente la unidad/PID propio registrado, nunca matar procesos OpenStack globalmente. Los IDs y configuraciones de recuperación se guardan antes de preparar recursos.

Un fallo de escenario se conserva. El siguiente caso sólo puede comenzar después de comprobar la prueba de restauración y VM OFF actuales. Si hay NEEDS_ATTENTION, se detiene toda nueva mutación y se usan ledger, backups y diagnósticos para reparar. No hay apagado forzado, borrado ciego ni eliminación de recursos ajenos. La restauración verifica rutas, bytes/propietarios/modos de configuración, servicios originales, inventario y allocations, ausencia de backends propios y hash XML; después permite apagado ordenado.

La aceptación oficial se ejecuta después del apagado: `validate_glance_campaign.py` verifica crudos, orden, cinco pares, parámetros, reloj, membresía de procesos, environment fijado, CPU/PSS, controles de host/invitado y restauración. `complete=true` del controlador no reemplaza ese análisis. Los directorios `accepted/acceptance.json` declaran el subconjunto aceptado; la cobertura completa se comprueba contra los dieciocho casos, conservando SHOW v3 aparte.

Para publicar resultados localmente se reutilizan `export_glance_results.py`, `plot_glance_comparison.py` y `glance_component_analysis.py`. Conservar CSV, PNG/PDF, procedencia y hashes. Separar CPU/PSS del API de Keystone/MySQL/Apache/generador/recolector. No atribuir un ahorro del proceso API al sistema completo. No ejecutar publicadores de Paolo ni ninguna automatización Git.
